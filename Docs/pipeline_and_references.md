## 1. Pipeline Architecture & Code Explanation

We do not have actual physical sensors plugged into our laptops. To build the edge parsers, we first had to write "dummy" generator code that perfectly mimics physical hardware behavior over a serial cable.

The codebase is split into three core layers:

### A. The Schemas (`schemas/*.json`)
These are strict JSON Draft-07 schemas acting as the single source of truth for what a payload must look like. If a payload violates these rules, it is rejected.
* **Why it matters:** It guarantees to the downstream Rule Engine that it will *never* crash due to a missing or malformed key.

### B. The "Dummy" Simulators (`synthetic_data/*.py`)
These scripts simulate the physics and Modbus/IO-Link behavior of the hardware over a 30-day period.
* **How the code works:** They use `datetime` loops and `random.uniform()` to generate base signals. They intentionally inject mathematical anomalies (e.g., a sudden 5°C spike to simulate wire insulation melting, or a `ZONE_D` critical vibration event). 
* **The output:** They format these variables into raw, comma-separated strings (just like a physical serial cable would output) and dump them into text files like `raw_modbus_dump.txt`. 

### C. The Edge Parsers (`edge/*.py`)
This is the actual production code that will run on the Teltonika Edge Gateway.
* **How the code works:** The parsers (e.g., `vibration_parser.py`) read the raw text streams line-by-line. They split the strings, cast the variables to exact floats/integers/enums, and construct a Python dictionary. 
* **The Validation Step:** Before outputting, the parser runs `jsonschema.validate()` against the corresponding schema. 
* **The Output:** Only if it passes validation, it converts the dictionary to JSON and appends it to a `.jsonl` file (e.g., `parsed_vibration_payloads.jsonl`), ready to be published via MQTT.

## 2. Standardized Output Format

Every sensor payload generated by our pipeline adheres to a strict, predictable JSON wrapper. This allows the downstream TimescaleDB and MQTT brokers to easily route the data without writing custom ingestion logic for every sensor.

**Example Output Payload:**
```json
{
  "device_id": "Schneider-HeatTag-01",
  "timestamp": "2026-07-15T14:32:00Z",
  "sensor_type": "gas_particle_sensor",
  "data": {
    "gas_concentration_ppm": 42.5,
    "micro_particle_index": 55.2,
    "internal_panel_temp_c": 38.1,
    "rate_of_thermal_rise_c_per_min": 1.2,
    "alert_severity_level": "WARNING"
  }
}
```
* **Routing:** Downstream systems look at the `"sensor_type"` key to know exactly which set of parameters is inside the `"data"` object.
